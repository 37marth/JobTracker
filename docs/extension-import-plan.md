# 지원내역 가져오기 계획

작성일: 2026-10-18

검토일: 2026-10-19. [전체 진행 계획](roadmap.md)의 로그인·회원별 검증·첫 배포 이후 재개를 검토한다. 아래 가져오기 설계는 보관하며 당장 구현하지 않는다.

상태: 구현 순서 보류. 2026-10-18 사용자 결정에 따라 [로그인과 사용자별 기록 관리](member-login-plan.md)를 먼저 진행한다. 기획 및 실제 페이지 확인 결과는 보관하며, 확장 프로그램과 가져오기 API는 미구현이다.
아래에서 '확정'은 사용자와 정한 기준이며, '제안'은 구현 전에 검토할 방법이다.

## 목적과 첫 버전 범위

사람인·잡코리아에 흩어진 지원내역을 다시 입력하는 수고를 줄인다. 로그인한 브라우저에서 지원내역 목록을 읽고, 사용자가 확인한 기록만 JobTracker에 저장한다.

- 확정: 사람인·잡코리아 우선 지원. 다른 사이트는 기존 JobTracker 화면에서 수동 등록한다.
- 방향: 공고를 보고 있었다는 이유로 지원했다고 판단하지 않고 실제 지원내역 목록을 출발점으로 삼는다.
- 제안: 첫 시제품은 현재 페이지의 한 건 미리 보기, 이후 한 건 저장, 마지막으로 여러 건 선택 저장까지 확장한다.
- 초기 검증은 로컬 서버에서 진행하되, 재개 시 로그인 회원에게 저장하는 흐름을 적용한다. 인터넷 공개 서비스와 확장 프로그램 스토어 배포는 별도 작업이다.
- 최초 버전은 다른 기간·다음 페이지를 자동 순회하거나 상시 동기화하지 않는다. 사용자가 연 기간·페이지의 기록만 대상으로 한다.

## 데이터 기준

| 항목 | 가져오기 기준 | 읽을 수 없을 때 |
| --- | --- | --- |
| 회사명 | 지원내역 목록의 회사명. 저장 전에 확인·수정 가능 | 필수 입력 안내 |
| 회사 위치 | **기업 정보의 기본 주소**. 공고의 근무지 주소로 대체하지 않는다 | 선택 입력으로 남김 |
| 직무 | 지원내역의 직무·지원 분야를 우선 사용. 공고 제목과 구분하고 수정 가능하게 표시 | 필수 입력 안내 |
| 지원 날짜 | 목록의 실제 지원일. 오늘은 가져온 날짜이므로 과거 지원일을 덮어쓰지 않는다 | 사용자가 실제 지원일 입력 |
| 메모 | 사용자가 선택 입력. 실제 근무지가 기업 주소와 다르면 여기에 기록 | 비워도 저장 가능 |
| 지원 상태 | 제안: 첫 버전은 지원완료로 등록하고 이후 기존 상태 변경 기능 사용 | 마감·열람만으로 합격·불합격을 추정하지 않음 |
| 출처 정보 | 제안: 사이트 종류, 원본 지원 기록 ID, 공고 링크를 보존 | 식별자가 불명확하면 자동 중복 판정을 보장하지 않음 |

위치 기준은 사용자 확정 사항이다. 기존 Company.location과 JobApplication.memo를 활용하며 지원별 근무지 필드는 추가하지 않는다. 기업 기본 주소도 과거 지원 당시 주소를 보장하지는 않는다.

## 브라우저에서 확인한 사실

- 두 사이트에서 회사명·실제 지원일·직무 또는 지원 분야·공고 링크가 DOM 텍스트로 읽혔다.
- 사람인은 지원 기록별 영역을 구분할 수 있었다. 잡코리아는 실제 지원 행과 추천공고 행이 따로 있어 추천공고를 제외할 근거를 확인했다.
- 사람인 진행 중 공고 한 건, 잡코리아 진행 중 한 건·마감 한 건에서 주소 정보를 확인했다. 근무지와 기업 정보의 주소 영역을 구분할 수 있었고, 서로 다른 주소인 사례도 있었다.
- 목록의 날짜·상태와 공고 상세의 날짜·상태는 의미가 다르므로 각각 구분해야 한다.
- 일부 숨겨진 안내 문구도 원시 textContent에 포함됐다. 단순 전체 텍스트 검색 대신 항목의 의미와 표시 상태에 맞춰 읽어야 한다.
- 확인한 표본 외의 삭제 공고·다중 주소·레이아웃과 자동 상세 조회 방식은 아직 검증하지 않았다. 모든 과거 기록이나 주소를 복원할 수 있다고 보장하지 않는다.

## 사용자 흐름 제안

1. 사람인 또는 잡코리아에서 로그인하고 원하는 기간의 지원내역 목록을 연다.
2. 확장 프로그램의 '지원내역 읽기'를 누른다.
3. 현재 페이지의 실제 지원 기록을 읽는다. 추천공고는 제외한다.
4. 사용자가 가져올 기록을 선택한다. 첫 버전에서는 지원취소 기록을 선택 불가로 표시하는 방안을 제안한다.
5. 선택한 기록에 필요한 기업 주소를 조회한다. 실패한 주소는 비워 두고 안내한다.
6. 회사명·기업 주소·직무·실제 지원일을 확인하고, 필요한 메모를 작성한다.
7. 저장 버튼을 눌러 JobTracker에 보낸다. 미리 보기만으로 저장하지 않는다.
8. 항목별로 저장 완료·이미 가져옴·실패를 표시한다. 실패 항목의 입력을 유지한다.
9. JobTracker 화면을 새로고침해 저장된 회사와 지원내역을 확인한다.

## 구현 순서와 완료 기준

| 단계 | 할 일 | 다음 단계로 넘어가는 기준 |
| --- | --- | --- |
| 1. 한 건 미리 보기 | 확장 프로그램 기본 틀과 입력창. 사람인 목록 한 건의 회사명·직무·지원일·출처를 읽어 표시 | 원본 화면과 값이 같고, 잡트래커 DB는 바뀌지 않음 |
| 2. 기업 주소와 두 사이트 지원 | 기업 주소 조회 방식 검증. 잡코리아용 읽기 추가. 추천공고 제외 | 두 사이트에서 각각 한 건 확인. 기업 주소와 근무지를 혼동하지 않고, 주소 실패에도 나머지 값을 유지 |
| 3. 한 건 저장 | 아래 가져오기 API와 중복 기준 구현. 기존 회사 재사용·새 회사 생성 처리 | 정상 저장, 다시 가져오기, 저장 실패 뒤 DB 상태를 재조회로 확인 |
| 4. 여러 건 선택 저장 | 선택한 기록을 순서대로 한 건씩 보내고 결과 표시 | 일부 실패 시 성공 건은 유지. 실패 건만 재시도해도 성공 건이 중복되지 않음 |
| 5. 마무리 | 회귀 확인, 사용법·제한사항 기록, 설치·실행 절차 정리 | 기존 수동 CRUD 유지, 두 사이트의 대표 사례 확인, 다음 사람이 실행 순서를 따라갈 수 있음 |

첫 구현 대상만 사람인으로 시작하고, 최종 첫 버전에는 두 사이트를 포함한다. 한꺼번에 전체 기능을 구현하지 않는다.

## 서버 처리 설계 제안

현재 회사 등록과 지원내역 등록은 각각 별도 API이며, JobApplicationRequestDto는 직무와 날짜를 필수로 받는다. 가져오기 전용 처리를 추가하고 기존 수동 등록 API는 유지한다.

가칭: POST /api/imports/job-applications (실제 구현 시 확정)

처리 순서:

1. 입력값과 지원 사이트를 검사한다. 브라우저에서 온 값도 서버에서 검증한다.
2. 출처 사이트와 원본 지원 기록 ID로 이미 가져온 내역인지 검사한다.
3. 이미 가져온 내역이면 기존 기록을 알리고 새로 저장하지 않는다. 기존 메모·상태를 덮어쓰지 않는다.
4. 기존 회사가 있으면 연결하고, 없으면 회사부터 생성한다.
5. 지원내역과 출처 정보를 저장한다.
6. 결과를 응답 DTO로 돌려준다.

새 회사 생성과 지원내역 저장은 한 트랜잭션으로 처리하는 방안을 제안한다. 지원내역 저장 실패 시 이번 요청이 만든 회사만 남지 않도록 한다. 여러 건 전체를 한 트랜잭션으로 묶지 않고 한 건 단위로 처리한다.

### 저장 단계 전에 정할 세부 기준

- 회사 매칭: 기존 이름 기준을 기본으로 하되 '(주)'와 '㈜', 공백 차이는 별도 확인이 필요하다. 문자열 모양만으로 다른 회사를 함부로 합치지 않는다. 애매하면 사용자가 기존 회사를 선택할 수 있게 하는 방안을 검토한다.
- 기존 회사의 위치: 가져온 주소로 기존 사용자 입력을 자동 덮어쓰지 않는 것을 기본 제안으로 한다.
- 중복 키: '사이트 + 원본 지원 기록 ID'를 우선 검토한다. '회사명'이나 '공고 ID'만으로 동일 지원 여부를 판정하지 않는다. 같은 공고 재지원·다른 사이트에서의 지원은 별도 기록일 수 있다.
- 원본 ID의 안정성과 잡코리아의 식별자 추출 방법은 저장 전에 검증한다. 식별자가 없으면 회사·날짜가 같다고 무조건 합치지 않는다.
- 출처 정보를 지원내역 필드에 둘지 별도 테이블에 둘지는 저장 단계에서 결정한다. DB 고유 제약과 동시 요청 실패 처리까지 함께 검토한다.
- 삭제한 가져오기 기록을 다시 가져올 수 있게 할지 결정한다. 첫 버전 제안은 사용자가 명시적으로 다시 선택하면 재등록 허용이다.
- 로그인·다중 사용자 기능을 먼저 추가하기로 했으므로, 중복 판정과 회사 매칭은 처음부터 로그인 회원 범위로 설계한다.

## 확장 프로그램의 책임과 권한

- 사이트마다 읽기 코드를 분리하고, 공통 입력창과 저장 처리는 공유한다.
- 사용자가 연 지원내역 화면을 읽고 확인된 값을 서버에 보낸다. DB에 직접 접속하지 않는다.
- 페이지 접근 권한과 JobTracker 서버 요청 권한은 필요한 범위로 제한한다. 전체 사이트 상시 접근을 기본값으로 삼지 않는다.
- 기업 주소는 실제 렌더링된 페이지에서 읽는 방법을 먼저 검증한다. 페이지 이동·추가 탭·요청 방식 중 무엇을 사용할지 2단계에서 결정한다. 현재 탭 읽기에 성공한 것과 백그라운드 상세 조회 성공은 별개다.
- 사이트 비밀번호나 로그인 쿠키를 수집·서버로 전송하지 않는다. 이력서·메시지 내용은 가져오기 대상이 아니다.
- 지원 취소·지원서 제출·기존 지원내역 삭제 버튼은 조작하지 않는다.
- 배포 전 사이트 이용 조건과 확장 프로그램 배포 요건을 별도 확인한다. 이번 확인은 기술적 가능성 조사다.

## 작은 검증 목록

1. 두 사이트의 정상 기록이 원본과 일치하고 추천공고는 제외되는가?
2. 과거 지원일을 보존하고 마감·열람을 합격·불합격으로 잘못 바꾸지 않는가?
3. 기업 주소와 근무지가 다르거나 주소를 읽지 못해도 올바르게 안내하는가?
4. 기존 회사 연결과 새 회사 등록이 모두 되고, 기존 회사의 위치·메모·상태를 덮어쓰지 않는가?
5. 같은 기록 재전송·빠른 연속 클릭·동시 요청이 중복을 만들지 않는가?
6. 서버 연결 실패·필수값 누락·저장 실패 후 입력과 DB 상태가 기대대로 유지되는가?
7. 여러 건 중 일부 실패 시 결과를 구분하고 실패 건만 재시도할 수 있는가?

읽기 테스트는 개인 지원 기록을 저장소에 넣지 않고 가상 데이터로 재현한다. 실제 사이트 확인과 자동 테스트 결과는 구분해 기록한다.

## 실제 기록 보관 전 준비

현재 개발 설정은 ddl-auto=create와 시작 시 예시 데이터 입력을 사용한다. 실데이터를 보관하기 전 테스트용 DB와 보관용 실행 설정을 분리하고, 백업·재시작 후 데이터 유지 여부를 확인한다. 이번 계획 작성에서는 설정을 변경하거나 서버를 재시작하지 않는다.

## 기술 학습의 연결

- 이번 기능: JavaScript 페이지 읽기, 입력 검증, DTO/API, 트랜잭션, 중복 방지, 테스트.
- 저장 흐름 확인 후 선택: Docker Compose로 앱·DB 실행 환경 정리, GitHub Actions로 자동 빌드·테스트, 이후 서버 배포.
- 여러 사람이 사용하는 서비스로 공개하기 전: 로그인과 사용자별 데이터 접근 권한.
- Redis·Kafka·다른 DB나 언어는 현재 기능의 전제조건이 아니다. 필요한 문제를 확인한 뒤 검토한다.

진행할 때는 한 단계의 요청 흐름과 실패 이유를 설명하고, 작은 변경으로 결과를 확인한 뒤 다음 단계로 넘어간다. 일정이나 완료율은 아직 산정하지 않는다.
