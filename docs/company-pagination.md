## 현재 요청 흐름

`/?page=1` → HomeController → CompanyService.indexPage(1) → PageRequest(1, 5, ID 내림차순) → Repository → 회사와 페이지 정보 → DTO 변환 → Model → Mustache.

- PageRequest: DB 조회에 전달할 페이지 번호·크기·정렬 조건.
- Page: 조회된 회사 목록과 전체 개수·페이지 수 등을 담는 결과.
- getContent(): 회사 목록을 꺼낸다. getTotalPages(): 전체 페이지 수를 꺼낸다.
- PageNumberDto: displayNumber는 화면 번호, requestPageNumber는 주소의 page 값이다.
- totalPages: DTO 목록. companiesTotalPages: 전체 페이지 수. 이름은 비슷하지만 담는 값이 다르다.
- 기존 GET /api/companies의 전체 목록 응답은 유지한다.

## 확인한 범위

- 실제 서버 GET: 회사 11개가 page=0에서 10개, page=1에서 1개로 나뉘며 응답은 200이다.
- 두 응답의 현재·전체 페이지 표시와 번호 1의 주소 page=0, 번호 2의 주소 page=1을 확인했다.
- 사용자가 실제 화면에서 회사 목록과 번호 링크 표시를 확인했다.
- Java 17 컴파일과 기존 GlobalExceptionHandlerTest 7건을 실행해 통과했다.
- 기존 GlobalExceptionHandlerTest는 기존 오류 응답을 검증하는 자산이다. 이 테스트의 통과를 페이징 자동 테스트 또는 사용자의 독립 테스트 작성 경험으로 표현하지 않는다.

## 확정한 화면 기준

- 회사는 한 페이지에 최대 5개, 페이지 번호는 최대 5개씩 묶는다.
- 3페이지의 >는 6페이지, 8페이지의 >는 11페이지다.
- 8페이지의 <는 1페이지, 13페이지의 <는 6페이지다.
- <<는 1페이지, >>는 실제 마지막 페이지다.
- 전체 7페이지라면 둘째 묶음에는 6, 7만 표시한다. 존재하지 않는 이동은 제공하지 않는다.
- 번호 5개는 표시 단위이며 저장할 회사 수를 제한하지 않는다.
- 지원내역 자체의 페이징은 이번 범위 밖이다.
