## 현재 요청 흐름

`/?page=1` → HomeController → CompanyService.indexPage(1) → PageRequest(1, 5, ID 내림차순) → Repository → 회사와 페이지 정보 → DTO 변환 → Model → Mustache.

- PageRequest: DB 조회에 전달할 페이지 번호·크기·정렬 조건.
- Page: 조회된 회사 목록과 전체 개수·페이지 수 등을 담는 결과.
- getContent(): 회사 목록을 꺼낸다. getTotalPages(): 전체 페이지 수를 꺼낸다.
- PageNumberDto: displayNumber는 화면 번호, requestPageNumber는 주소의 page 값이다.
- totalPages: DTO 목록. companiesTotalPages: 전체 페이지 수. 이름은 비슷하지만 담는 값이 다르다.
- 기존 GET /api/companies의 전체 목록 응답은 유지한다.

## 확인한 범위

- 실제 서버 GET: 회사 11개가 page=0에서 10개, page=1에서 1개로 나뉘며 응답은 200이다.
- 두 응답의 현재·전체 페이지 표시와 번호 1의 주소 page=0, 번호 2의 주소 page=1을 확인했다.
- 사용자가 실제 화면에서 회사 목록과 번호 링크 표시를 확인했다.
- Java 17 컴파일과 기존 GlobalExceptionHandlerTest 7건을 실행해 통과했다.
- 기존 GlobalExceptionHandlerTest는 기존 오류 응답을 검증하는 자산이다. 이 테스트의 통과를 페이징 자동 테스트 또는 사용자의 독립 테스트 작성 경험으로 표현하지 않는다.

## 확정한 화면 기준

- 회사는 한 페이지에 최대 5개, 페이지 번호는 최대 5개씩 묶는다.
- 3페이지의 >는 6페이지, 8페이지의 >는 11페이지다.
- 8페이지의 <는 1페이지, 13페이지의 <는 6페이지다.
- <<는 1페이지, >>는 실제 마지막 페이지다.
- 전체 7페이지라면 둘째 묶음에는 6, 7만 표시한다. 존재하지 않는 이동은 제공하지 않는다.
- 번호 5개는 표시 단위이며 저장할 회사 수를 제한하지 않는다.
- 지원내역 자체의 페이징은 이번 범위 밖이다.

## 학습 방식과 현재 진도

사용자가 직접 코드를 작성하고, 설명·힌트를 받은 뒤 검토와 실행 확인을 진행한다. 새로운 개념은 한 번에 하나씩 다룬다. 다음 단계의 기능을 미리 구현하지 않는다. 숫자 목록 → DTO 목록 → Mustache 반복 출력 → 5개 묶음 계산 → 화살표 이동 → 현재 번호 판별 → 빈 목록·범위 검사까지 작성했다. CSS와 자동 테스트는 AI에게 맡겼다. 다음은 세션 기반 자체 로그인 기초다.


## 가운데 배치와 현재 페이지 강조 — 2026-11-10

- 사용자가 PageNumberDto에 boolean currentPage를 추가하고 반복문에서 i == page + 1로 판별해 생성자에 전달했다.
- 화면과 CSS는 AI에게 맡겼다. nav.pagination과 .pagination-links로 목록 아래 가운데 정렬, 링크의 버튼 모양·간격·포커스 스타일을 적용했다.
- totalPages 반복 안의 currentPage는 DTO의 boolean이다. true인 링크에 is-current 클래스와 aria-current=page를 붙여 파란색으로 강조한다. 반복 밖 요약의 currentPage는 Model의 화면 번호다.
- 자동 검증: 기존 13개 페이징 예시에서 현재 링크 하나에만 강조가 붙는지 추가 검증했다. 기존 오류 응답 7건과 함께 통과했다.
- 실제 템플릿·서비스·컨트롤러와 조회 대역으로 만든 화면을 브라우저에서 확인했다. 화면 8 / 13페이지에서 << < 6 7 [8] 9 10 > >> 표시와 좁은 화면 가운데 배치를 확인했다.
- localhost:8080은 당시 응답 시간 초과로 실제 DB 화면 검증을 하지 못했다. DB·서버를 재시작하지 않았다. 미리보기는 build/reports/pagination-preview에 생성한다.
- 다음은 실제 서버 반영 확인과 페이지 경계 상황 정리다. 자동 커밋·푸시는 하지 않았다.


## 빈 목록의 페이지 영역 숨김 — 2026-11-10

- 사용자가 Model에 hasPages = companiesTotalPages > 0을 전달하고 Mustache의 nav 전체를 조건 블록으로 감쌌다.
- 회사가 없으면 등록된 회사가 없다는 안내는 유지하고 페이지 문구와 링크를 숨긴다.
- HomePaginationTest에 hasPages 값, nav 표시 여부, 빈 목록 문구 유지와 1 / 0 문구 제거 검증을 추가했다. DB 없는 13개 예시가 통과했다. 실제 개발 DB의 회사 삭제는 수행하지 않았다.
- 다음은 음수 요청의 첫 페이지 이동, 범위 초과 번호와 삭제 후 페이지 보정이다. 서버 로직은 사용자 직접 작성 방식으로 진행한다.

## 잘못된 번호와 삭제 후 마지막 페이지 처리 — 2026-11-10

- 사용자가 음수 검사와 범위 초과 시 리다이렉트를 직접 작성했다. 음수를 조회한 뒤 검사하면 PageRequest가 먼저 예외를 내므로, 검사 순서를 조회 앞으로 옮겼다.
- 전체 페이지가 6이면 유효 요청 번호는 0~5다. page >= companiesTotalPages인 요청은 companiesTotalPages - 1로 이동한다. 문자열 연결 전에 뺄셈하도록 괄호를 사용했다.
- 전체 페이지가 0인 빈 목록은 리다이렉트 대상에서 제외한다. -1과 0 사이를 왕복하는 상황을 막고 빈 목록 안내를 출력한다.
- 사용자 실행 확인: -999 → page=0, 999 → page=5. 회사 1·2를 삭제해 회사 24개가 되자 page=4의 마지막 5페이지로 이동했고 회사 6·5·4·3이 표시됐다. 가운데 배치와 현재 번호 강조도 사용자 화면에서 확인했다.
- AI의 자동 검증은 개발 DB 삭제 없이 조회 결과 대역으로 수행한다. 빈 목록, 현재 번호 강조, 번호·화살표 이동과 음수·범위 초과·삭제 후 줄어든 페이지 사례를 확인한다. 상세 실행 결과는 아래에 기록한다.
- 오늘 학습: CSS class 연결, Mustache의 boolean 조건 블록, 0부터 시작하는 요청 번호, 조회 전 검사, return과 redirect의 흐름, && 조건과 괄호의 계산 순서.
