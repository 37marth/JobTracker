# 로그인과 사용자별 기록 관리 계획

작성일: 2026-10-18

검토일: 2026-10-30. 전체 순서·테스트·배포·후속 확장 기준은 [진행 계획](roadmap.md)을 따른다. 사용자 요청으로 회사 페이징 → 세션 기반 자체 로그인 → 회원별 기록 분리 → 구글 소셜 로그인 순서로 변경했다. 이 문서는 로그인 세부 설계다.

상태: 확장 방향 확정, 구현 전. 기존 CRUD의 완료 상태와 구분한다.

## 목적과 우선순위

여러 사람이 각자의 회사와 지원내역을 관리하도록 만든다. 사용자는 확장 프로그램보다 로그인과 사용자별 기록 분리를 먼저 진행하기로 선택했다. 사람인·잡코리아 가져오기 계획은 보관하고 이후 다시 진행한다.

## 첫 버전의 범위

- 첫 단계는 자체 회원가입·로그인·로그아웃이다. 회원별 기록 분리를 확인한 뒤 구글 로그인을 추가한다. 카카오·네이버 등 다른 제공자는 첫 배포 이후 검토한다.
- 로그인한 회원의 회사·지원내역만 조회·등록·수정·삭제.
- 회사 이름 중복 검사는 회원별로 적용. 다른 회원끼리는 같은 회사 이름을 등록할 수 있다.
- 다른 회원의 회사·지원내역 ID를 직접 보내도 접근을 거절한다. 상태 변경과 회사 연쇄 삭제도 포함한다.
- 구현 방향은 Spring Security와 서버 세션이다. 여러 로그인 버튼 지원과 여러 소셜 계정을 하나의 회원으로 연결하는 기능은 구분한다. 초기에는 제공자가 다른 계정은 별도 회원으로 취급하고, 이름·이메일 일치만으로 자동 연결하지 않는다.
- 자체 비밀번호 가입은 이번 범위에 포함한다. 비밀번호는 Spring Security PasswordEncoder로 단방향 해시를 저장한다. 비밀번호 재설정·탈퇴 등 실제 운영의 계정 관리 범위는 공개 전에 정한다. 여러 계정 연결, 관리자 화면, JWT는 지금 구현하지 않는다.
- 로컬에서 두 계정으로 검증한 뒤 인터넷 배포를 별도 진행한다. 로그인 구현 자체가 공개 배포 완료를 뜻하지 않는다.

## 데이터 관계 제안

```text
회원(Member) 1 ── N 회사(Company) 1 ── N 지원내역(JobApplication)
```

Company는 공유 기업 사전이 아니라 회원 개인이 등록한 회사 기록으로 다룬다. Company에 회원 연결을 추가하고 지원내역의 주인은 연결된 회사의 회원으로 판단한다. 지원내역에 회원 ID를 중복 저장하지 않는 방향으로 시작한다.

기존 id, provider, providerId, name 네 필드안은 구글 로그인만 고려한 과거 제안이다. 자체 로그인도 포함하도록 로그인 작업 시작 시 회원 필드를 다시 정한다. 내부 회원 ID와 로그인 식별자를 구분하며 비밀번호 원문은 저장하지 않는다. 구글은 sub를 providerId에 대응시키고, 변경 가능한 이메일이나 표시 이름만으로 계정을 합치지 않는다. 구글 계정 연결 전 (provider, providerId)의 DB 중복 방지를 적용·검증한다.

요청 본문에서 전달한 회원 ID를 소유자로 신뢰하지 않고, 서버가 확인한 로그인 정보에서 회원을 찾는다.

## 작은 단계로 진행

1. 회사 페이징을 마친 뒤 회원·회사 관계와 회원별 중복 기준, 자체·소셜 로그인을 위한 Member 필드를 정한다.
2. Spring Security 세션 기반 자체 회원가입·로그인·로그아웃을 구현한다. 가입 입력 검증과 계정 중복, 비밀번호 해시 검증을 확인한다.
3. 로그인 계정과 내부 회원을 연결하고 Company 소유자를 추가한다. 기존 데이터의 소유자 지정 방법과 테스트 데이터 준비 방법을 먼저 정한다. 기존 데이터를 임의 삭제하거나 첫 로그인 회원에게 배정하지 않는다.
4. 홈 화면과 모든 API에서 회원 범위로 조회·변경하도록 적용한다. 회사 이름 중복 검사와 지원내역 상태 변경·연쇄 삭제를 포함한다. (member_id, name) DB 고유 제약과 그 위반에 대한 오류 처리도 적용한다. 현재 정확한 이름 비교 기준을 유지하며 별칭 통합은 하지 않는다.
5. 기존 fetch 요청에 CSRF 보호를 연동하고 로그인 만료·로그아웃 후 처리를 확인한다. 요청이 실패한다는 이유로 CSRF 보호를 통째로 끄지 않는다.
6. 두 계정으로 정상 사용과 다른 회원 데이터 접근 거절을 검증한다. 기존 CRUD 테스트도 로그인 전제에 맞게 수정한다. 테스트는 각 단계에서 조금씩 추가하고, 기존 오류 테스트만으로 Security 적용과 실제 DB 동시 중복 방지를 검증했다고 하지 않는다.
7. 구글 로그인을 추가하고 최초 가입·재로그인·취소·실패 및 동일한 회원별 접근 제한을 확인한다. 비밀값은 환경변수로 관리하고, 같은 이메일의 자체 계정과 자동 연결하지 않는다.

각 단계마다 요청 흐름과 변경 이유를 설명한 뒤 다음으로 넘어간다. 로그인만 연결된 중간 버전을 다른 사람이 사용하도록 공개하지 않는다.

## 완료 확인 기준

- 로그인하지 않은 요청은 화면과 API에 맞는 안내 또는 거절을 받는다.
- 두 회원은 같은 이름의 회사를 각각 등록할 수 있고 자기 회사 중복은 거절된다.
- 회원 A가 회원 B의 ID로 목록 조회·지원 등록·정보 수정·상태 변경·삭제를 요청해도 B의 데이터가 노출되거나 변경되지 않는다.
- 회사 삭제는 해당 회원의 해당 회사와 연결된 지원내역에만 영향을 준다.
- 로그아웃 뒤 기존 세션으로 보호된 기능에 접근할 수 없다.
- 기존 CRUD·입력 오류 안내·목록 정렬·화면 동작이 유지된다.

실데이터 보관 전에는 현재 ddl-auto=create 및 예시 데이터 초기화 설정을 개발용과 분리하고, 재시작 후 데이터 보존을 확인한다. 외부 공개에는 HTTPS, 비밀값 관리, 백업 등 배포 준비가 별도로 필요하다.

## 확장 프로그램과의 연결

로그인과 회원별 접근 검증·첫 배포를 마친 뒤 [지원내역 가져오기 계획](extension-import-plan.md)의 재개 여부를 정한다. 가져올 회사 매칭과 출처 기록 중복 검사도 로그인 회원 범위로 적용한다. 확장 프로그램에서 서버로 로그인 상태를 안전하게 전달하는 방법은 재개 시 별도로 설계한다. JobTracker 소셜 로그인은 채용 사이트의 로그인이나 지원내역 API 접근 권한을 대신하지 않는다.

## 바로 다음 작업

현재는 회사 목록 페이징을 진행한다. 그다음 자체 로그인에 맞는 회원 필드와 회원가입 흐름부터 작은 단위로 구현한다. Company 소유자 연결은 기존 데이터 처리 방안을 정한 뒤 진행한다.
