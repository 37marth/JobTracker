# 로그인과 사용자별 기록 관리 계획

작성일: 2026-10-18

검토일: 2026-11-19. 전체 순서·테스트·배포·후속 확장 기준은 [진행 계획](roadmap.md)을 따른다. 현재 순서는 완료한 회사 페이징 → 세션 기반 자체 로그인 → 회원별 기록 분리 → 검증·데이터 보존과 첫 배포 → 구글 소셜 로그인이다. 이 문서는 로그인 세부 설계다.

상태: 사용자가 회원 엔티티·DTO·리포지토리, 회원가입 서비스의 중복 검사·해시·저장, PasswordEncoder 빈, 중복 아이디 409 예외 처리를 작성했다. MemberApiController에 POST /api/members/signup, @Valid @RequestBody, 서비스 호출과 ResponseEntity<Void>의 201 응답까지 연결했다. AI의 설명·예시·코드 검토를 받으며 사용자가 직접 입력했다. 2026-11-19 실행 중인 서버에서 AI가 정상 가입 201·중복 409·빈 아이디와 빈 비밀번호 각각 400을 확인했다. 사용자가 DB에서 BCrypt 해시 저장을 확인했다. 로그인·세션 검증은 남아 있다. (수정: [2026-11-21 Claude], Codex 지적 반영)

## 목적과 우선순위

여러 사람이 각자의 회사와 지원내역을 관리하도록 만든다. 사용자는 확장 프로그램보다 로그인과 사용자별 기록 분리를 먼저 진행하기로 선택했다. 사람인·잡코리아 가져오기 계획은 보관하고 이후 다시 진행한다.

## 첫 버전의 범위

- 첫 단계는 자체 회원가입·로그인·로그아웃이다. 회원별 기록 분리와 데이터 보존을 검증해 첫 배포한 뒤 구글 로그인을 추가한다. 카카오·네이버 등 다른 제공자도 후속 범위다.
- 로그인한 회원의 회사·지원내역만 조회·등록·수정·삭제.
- 회사 이름 중복 검사는 회원별로 적용. 다른 회원끼리는 같은 회사 이름을 등록할 수 있다.
- 다른 회원의 회사·지원내역 ID를 직접 보내도 접근을 거절한다. 상태 변경과 회사 연쇄 삭제도 포함한다.
- 구현 방향은 Spring Security와 서버 세션이다. 여러 로그인 버튼 지원과 여러 소셜 계정을 하나의 회원으로 연결하는 기능은 구분한다. 초기에는 제공자가 다른 계정은 별도 회원으로 취급하고, 이름·이메일 일치만으로 자동 연결하지 않는다.
- 자체 비밀번호 가입은 이번 범위에 포함한다. 비밀번호는 Spring Security PasswordEncoder로 단방향 해시를 저장한다. 비밀번호 재설정·탈퇴 등 실제 운영의 계정 관리 범위는 공개 전에 정한다. 여러 계정 연결, 관리자 화면, JWT는 지금 구현하지 않는다.
- 로컬에서 두 계정으로 검증한 뒤 인터넷 배포를 별도 진행한다. 로그인 구현 자체가 공개 배포 완료를 뜻하지 않는다.

## 데이터 관계 제안

```text
회원(Member) 1 ── N 회사(Company) 1 ── N 지원내역(JobApplication)
```

Company는 공유 기업 사전이 아니라 회원 개인이 등록한 회사 기록으로 다룬다. Company에 회원 연결을 추가하고 지원내역의 주인은 연결된 회사의 회원으로 판단한다. 지원내역에 회원 ID를 중복 저장하지 않는 방향으로 시작한다.

기존 id, provider, providerId, name 네 필드안은 구글 로그인만 고려한 과거 제안이다. 현재 사용자가 작성한 필드는 Long id, String loginId, String password다. password에는 가입 처리에서 해시한 값을 넣는다. 내부 회원 ID와 로그인 식별자를 구분하며 비밀번호 원문은 저장하지 않는다. 구글 로그인 확장 시에는 식별 정보의 저장 구조를 별도로 설계한다. 구글은 sub를 providerId에 대응시키고, 변경 가능한 이메일이나 표시 이름만으로 계정을 합치지 않는다. 구글 계정 연결 전 (provider, providerId)의 DB 중복 방지를 적용·검증한다.

요청 본문에서 전달한 회원 ID를 소유자로 신뢰하지 않고, 서버가 확인한 로그인 정보에서 회원을 찾는다.

## 작은 단계로 진행

1. 회사 페이징을 마친 뒤 회원·회사 관계와 회원별 중복 기준, 자체·소셜 로그인을 위한 Member 필드를 정한다.
2. Spring Security 세션 기반 자체 회원가입·로그인·로그아웃을 구현한다. 가입 입력 검증과 계정 중복, 비밀번호 해시 검증을 확인한다.
3. 로그인 계정과 내부 회원을 연결하고 Company 소유자를 추가한다. 기존 데이터의 소유자 지정 방법과 테스트 데이터 준비 방법을 먼저 정한다. 기존 데이터를 임의 삭제하거나 첫 로그인 회원에게 배정하지 않는다.
4. 홈 화면과 모든 API에서 회원 범위로 조회·변경하도록 적용한다. 회사 이름 중복 검사와 지원내역 상태 변경·연쇄 삭제를 포함한다. (member_id, name) DB 고유 제약과 그 위반에 대한 오류 처리도 적용한다. 현재 정확한 이름 비교 기준을 유지하며 별칭 통합은 하지 않는다.
5. 기존 fetch 요청에 CSRF 보호를 연동하고 로그인 만료·로그아웃 후 처리를 확인한다. 요청이 실패한다는 이유로 CSRF 보호를 통째로 끄지 않는다.
6. 두 계정으로 정상 사용과 다른 회원 데이터 접근 거절을 검증한다. 기존 CRUD 테스트도 로그인 전제에 맞게 수정한다. 테스트는 각 단계에서 조금씩 추가하고, 기존 오류 테스트만으로 Security 적용과 실제 DB 동시 중복 방지를 검증했다고 하지 않는다.
7. 데이터 보존·공개 전 검증을 마치고 자체 로그인 버전을 첫 배포한다. 이후 구글 로그인을 추가하고 최초 가입·재로그인·취소·실패 및 동일한 회원별 접근 제한을 확인한다. 비밀값은 환경변수로 관리하고, 같은 이메일의 자체 계정과 자동 연결하지 않는다.

각 단계마다 요청 흐름과 변경 이유를 설명한 뒤 다음으로 넘어간다. 로그인만 연결된 중간 버전을 다른 사람이 사용하도록 공개하지 않는다.

## 완료 확인 기준

- 로그인하지 않은 요청은 화면과 API에 맞는 안내 또는 거절을 받는다.
- 두 회원은 같은 이름의 회사를 각각 등록할 수 있고 자기 회사 중복은 거절된다.
- 회원 A가 회원 B의 ID로 목록 조회·지원 등록·정보 수정·상태 변경·삭제를 요청해도 B의 데이터가 노출되거나 변경되지 않는다.
- 회사 삭제는 해당 회원의 해당 회사와 연결된 지원내역에만 영향을 준다.
- 로그아웃 뒤 기존 세션으로 보호된 기능에 접근할 수 없다.
- 기존 CRUD·입력 오류 안내·목록 정렬·화면 동작이 유지된다.

실데이터 보관 전에는 현재 ddl-auto=create 및 예시 데이터 초기화 설정을 개발용과 분리하고, 재시작 후 데이터 보존을 확인한다. 외부 공개에는 HTTPS, 비밀값 관리, 백업 등 배포 준비가 별도로 필요하다.

## 확장 프로그램과의 연결

로그인과 회원별 접근 검증·첫 배포를 마친 뒤 [지원내역 가져오기 계획](extension-import-plan.md)의 재개 여부를 정한다. 가져올 회사 매칭과 출처 기록 중복 검사도 로그인 회원 범위로 적용한다. 확장 프로그램에서 서버로 로그인 상태를 안전하게 전달하는 방법은 재개 시 별도로 설계한다. JobTracker 소셜 로그인은 채용 사이트의 로그인이나 지원내역 API 접근 권한을 대신하지 않는다.

## 2026-11-19 학습 마무리

### 커밋 이후 실제 회원가입 API 확인

- 사용자가 서버를 실행한 뒤 AI가 localhost:8080에 POST 요청을 보냈다. 테스트 아이디는 signup_check_20261119_164232다. 테스트 회원 1건을 생성했으며 삭제하지 않았다.
- 정상 가입: HTTP 201, 빈 응답 본문. 같은 아이디 재가입: HTTP 409, ‘이미 존재하는 아이디입니다.’
- 공백 아이디: HTTP 400, ‘아이디를 입력하세요.’ 공백 비밀번호: HTTP 400, ‘비밀번호를 입력하세요.’
- 비밀번호 해시 전달 코드는 확인했으나 DB 직접 조회는 접속 비밀번호가 없어 수행하지 못했다. 실제 저장 해시 조회·비밀번호 matches 검증과 로그인 성공을 확인한 것으로 표현하지 않는다.
- 아래 커밋 전 테스트 기록은 이전 확인 범위다. 이번 실제 API 확인과 구분한다.

- 학습한 흐름: 중복이면 throw로 가입 진행 중단 → @ExceptionHandler가 해당 예외 처리 → ErrorResponseDto와 HTTP 409 응답.
- 비밀번호 원문을 DTO에서 덮어쓰지 않고 서비스에서 encode한 값을 toEntity(encodedPassword)에 전달한다.
- PasswordEncoder는 인터페이스이고 BCryptPasswordEncoder는 구현체다. @Configuration·@Bean으로 객체를 등록하고 @Autowired로 서비스에 주입하는 흐름을 다뤘다. 개념 숙달이나 독립 재구현 완료로 표현하지 않는다.
- 로그인 목업은 보관했으며 실제 회원가입·로그인 화면 연결은 남아 있다.
- 커밋 전 검증: Java 17로 컴파일 성공. 개발 DB를 사용하지 않는 기존 HomePaginationTest 19건과 GlobalExceptionHandlerTest 7건, 합계 26건 통과. AI가 실행한 기존 기능 회귀 확인이며 새 회원가입·해시 저장·중복 아이디 응답을 실행 검증한 결과는 아니다. 서버 시작이나 개발 DB 변경은 하지 않았다.

## 사용자 로그인 화면 목업 — 2026-11-18

- 사용자가 그림판으로 그린 배치를 화면 구현 기준으로 보관한다. [사용자 원본](mockups/login-user-sketch-original.png), [흰 배경 확인본](mockups/login-user-sketch-preview.png). 원본은 투명 배경에 검은 선이라 검은 뷰어 배경에서는 보이지 않을 수 있다. 확인본은 같은 그림을 흰 배경에 겹친 것이며 원본도 그대로 보존했다.
- 위쪽 JobTracker 로고 → 중앙 아이디 입력칸 → 비밀번호 입력칸 → 로그인 버튼 → ‘계정이 없나요? 회원가입’ 링크 순서다.
- 회원가입 링크는 AI가 제안했고 사용자가 포함하기로 명시적으로 동의했다. 별도 회원가입 화면으로 들어가는 동선이다.
- 하단 동그라미 네 개는 이후 소셜 로그인 버튼을 둘 영역이다. 제공자 네 개 동시 구현을 확정한 뜻은 아니다. 첫 배포에는 동작하지 않는 소셜 버튼을 먼저 노출하지 않고 자체 로그인과 회원가입 동선부터 만든다.
- 로그인 성공 후 본인의 회사 목록으로 이동하는 방향으로 연결한다. 간격·색상 등 세부 CSS와 실패 안내 배치는 화면 구현 단계에서 정한다. 목업 보관은 로그인 화면 구현 완료를 의미하지 않는다.
- 지금은 서버 회원가입 처리 학습을 이어간다. 목업 제시를 화면·인증 전체 구현 위임으로 해석하지 않는다.
