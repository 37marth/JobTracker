# 문제 해결 기록

## 회사 정보를 수정하면 목록 위치가 바뀌는 문제

- 기록일: 2026-10-12
- 진행 상태: 코드 적용 완료. 회사 수정 후 목록 순서 유지와 ID 오름차순 표시를 사용자 수동 확인.

### 겪은 문제

회사 목록이 `회사 1 → 회사 2 → 회사 3` 순서로 보였다. 회사 1의 정보를 수정하고 화면을 다시 불러오니 `회사 2 → 회사 3 → 회사 1`로 바뀌었다.

사용자는 이름이나 위치만 고쳤는데 목록 위치까지 바뀌면 수정한 회사를 다시 찾아야 한다. 회사 정보를 수정해도 목록 위치가 유지되어야 한다고 판단했다.

### 원인

`CompanyService.index()`는 `companyRepository.findAll()`로 회사 목록을 조회하고 있었다. 조회할 때 정렬 기준을 지정하지 않아 DB에서 반환하는 순서가 보장되지 않았다. 화면은 받은 목록 순서대로 회사를 표시하고 있었다.

### 선택한 해결 방법

회사 ID가 작은 순서대로 조회하도록 정렬 기준을 추가하기로 했다. 회사 이름과 위치를 수정해도 ID는 바뀌지 않으므로, 같은 회사 목록의 순서를 유지할 수 있다.

이름순은 이름을 수정하면 위치가 바뀔 수 있고, 수정 시각순도 수정할 때마다 위치가 바뀔 수 있다. 현재 요구사항에는 ID순이 맞다고 판단했다. 사용자가 직접 순서를 바꾸는 기능은 이번 작업 범위에 포함하지 않는다.

`CompanyRepository`에 다음 메서드를 추가하고 `CompanyService.index()`에서 호출하도록 변경했다.

```java
// CompanyRepository: java.util.List import 필요
List<Company> findAllByOrderByIdAsc();

// CompanyService.index(): 기존 findAll() 호출을 교체
List<Company> companies = companyRepository.findAllByOrderByIdAsc();
```

`OrderByIdAsc`는 ID 기준 오름차순 정렬을 뜻하며, SQL의 `ORDER BY id ASC`에 해당한다. 이름·위치를 저장하는 수정 로직은 그대로 사용한다.

### 확인 결과

- 리포지토리의 정렬 메서드와 서비스 호출이 실제 코드에 반영된 것을 확인했다.
- Java 17의 `compileJava` 검사를 통과했다.
- 사용자가 화면에서 수정 후 순서가 유지되고 ID 오름차순으로 표시되는 것을 수동 확인했다.
- 자동화된 화면 클릭이나 API 수정·재조회 검증은 이번 정렬 변경에서 수행하지 않았다.

현재 설정은 `ddl-auto=create`이므로 서버를 재실행하면 테스트 데이터가 초기화된다. 실행 후 테스트 데이터를 준비한다.

### 배운 점

전체 목록을 조회한다는 것과 원하는 순서로 조회한다는 것은 별개다. 화면에 일정한 순서가 필요하면 DB의 반환 순서에 기대지 않고 조회 코드에 정렬 기준을 명시해야 한다.

### 지원내역에도 같은 해결 방법 적용

지원내역 수정 화면을 테스트하면서 수정한 지원내역의 위치도 바뀌는 문제가 발견됐다. 회사 목록에서 확인한 원인을 바탕으로, 회사별 지원내역 조회에도 ID 오름차순 정렬을 적용했다.

```java
// JobApplicationRepository
List<JobApplication> findByCompanyIdOrderByIdAsc(Long companyId);

// JobApplicationService.index(): 기존 findByCompanyId() 호출을 교체
return jobApplicationRepository.findByCompanyIdOrderByIdAsc(companyId)
        .stream()
        .map(jobApplication -> createJobApplicationDto(jobApplication))
        .collect(Collectors.toList());
```

`CompanyId` 조건은 유지해 해당 회사의 지원내역만 가져오고, `OrderByIdAsc`로 그 목록의 순서를 정한다. 회사 전체 조회와 특정 회사의 지원내역 조회는 범위가 다르므로 조회 조건을 없애지 않았다.

리포지토리와 서비스의 연결, Java 17 컴파일 검사를 확인했다. 사용자가 화면에서 수정 동작과 순서 유지를 수동 확인했다. 이번에도 자동화된 화면 클릭이나 API 수정·재조회 검증은 수행하지 않았다.

## 입력 오류가 나도 원인을 알기 어려운 문제

- 기록일: 2026-10-15
- 진행 상태: 입력 검증 오류의 응답과 화면 안내 적용·확인 완료.

### 겪은 문제와 원인

필수값을 비우고 등록·수정하면 400으로 거절되지만, 화면에는 상태 코드나 일반 실패 문구만 나왔다. 사용자는 어떤 입력을 고쳐야 하는지 알기 어려웠다. 기본 오류 응답에 입력 조건의 메시지를 넣고 화면에서 읽는 연결이 필요했다.

### 선택한 해결 방법

`GlobalExceptionHandler`가 `@Valid` 실패 예외에서 필드 오류 문장 하나를 꺼내 `ErrorResponseDto.message`에 담아 400으로 반환한다. 화면의 공통 함수가 JSON의 `message`를 읽고 해당 등록·수정 영역에 표시한다. 실패할 때 입력값과 회사 펼침 상태를 유지하고, 새 요청이나 수정 취소 시 이전 오류를 지운다. 문구가 없거나 응답을 읽지 못하면 기본 안내를 표시한다.

### 확인 결과

DB 없는 요청 테스트로 빈 회사명·날짜 누락의 400과 안내 문장, 정상 등록 201, 없는 대상 수정 404를 확인했다. 실제 브라우저에서 회사·지원내역 등록·수정의 필수값 오류, 입력값 유지, 정상 재요청과 취소 시 오류 제거를 확인했다. 거절된 수정은 저장값을 바꾸지 않았고, 확인용 데이터 정리 후 기존 데이터도 유지되었다.

## 위치를 비웠는데 '미입력' 안내가 나오지 않는 문제

- 기록일: 2026-10-15
- 진행 상태: 화면용 값 변환 적용, 템플릿 검사와 실제 브라우저 확인 완료.

### 겪은 문제와 원인

위치는 선택사항인데 빈 문자열로 등록하면 목록에 `위치:`만 표시되었다. 기존 Mustache 섹션 조건이 빈 문자열을 없는 값으로 판단하지 않아 '미입력' 안내를 표시하지 못했다.

### 선택한 해결 방법

`CompanyViewDto.getLocationDisplay()`에서 null·빈 문자열·공백뿐인 값을 검사한다. 비어 있으면 '미입력', 실제 위치가 있으면 원래 값을 반환한다. 목록은 `{{locationDisplay}}`를 사용하고 수정 입력칸은 기존 `{{location}}`를 사용한다. 안내 문장을 DB에 저장하거나 수정 입력칸의 실제 값으로 채우지 않는다.

### 확인 결과

실제 템플릿에 null·빈 문자열·공백·일반 위치·HTML 문자가 포함된 위치를 넣어 표시 결과와 원래 수정값 유지를 확인했다. 브라우저에서도 '위치: 미입력'과 빈 수정칸을 확인했고, 확인용 회사 정리 후 기존 회사 정보가 유지되었다.

## 같은 회사가 여러 번 등록되는 문제

- 기록일: 2026-10-15
- 진행 상태: 등록 중복 검사와 409 응답 적용, 자동 검사 통과. 수정 검사와 실제 DB·화면 확인은 남음.

### 겪은 문제와 판단 기준

같은 이름으로 등록을 반복하면 ID만 다른 회사가 생겼다. 한 회사의 여러 지원 기록을 같은 회사 아래에 모으기 위해 회사 이름이 같으면 중복으로 처리하기로 했다. 위치는 선택사항이므로 중복 기준에서 제외했다.

### 선택한 해결 방법

`CompanyService.create()`에서 `existsByName()`으로 저장 전에 검사한다. 이름이 존재하면 `DuplicateCompanyException`을 던져 저장을 중단한다. `GlobalExceptionHandler`는 이 예외만 받아 409와 '이미 등록된 회사입니다.'라는 메시지를 반환한다. 화면은 입력 검증의 400뿐 아니라 중복의 409에서도 같은 오류 표시 함수를 사용한다. 서비스에 검사를 두어 화면 외의 API 요청에도 적용한다.

### 확인 결과와 남은 범위

실제 컨트롤러·서비스·예외 처리기에 리포지토리 대역을 연결한 테스트로 중복일 때 저장을 호출하지 않고 409와 메시지를 반환하는 것을 확인했다. 오류 응답 테스트 7건과 공통 화면 오류 표시 함수 검사 7건을 통과했다. 실제 DB와 브라우저에서 중복 등록을 막는 확인은 서버 재실행 후 진행한다.

회사 수정에는 검사를 아직 적용하지 않았다. 다음에는 수정하는 회사 자신을 제외하고 다른 회사와 이름이 겹치는지 검사한다. 현재 이름의 앞뒤 공백 제거와 DB 고유 제약은 적용하지 않았으며, 동시 등록 요청의 중복 방지는 검증하지 않았다.
