# 다음 버전 진행 계획

검토일: 2026-11-09

2026-10-30 사용자 결정: 페이징을 먼저 적용하고, 자체 로그인과 소셜 로그인을 모두 학습·구현한다. 자체 로그인은 Spring Security의 서버 세션으로 시작하며 JWT는 이번 범위에 넣지 않는다. 개발 작업은 현재 대화, 개념 학습은 별도 대화에서 진행한다.

이 문서가 작업 순서와 완료 기준의 기준 문서다. 로그인 세부 설계는 [회원 계획](member-login-plan.md), 이후 가져오기는 [확장 프로그램 계획](extension-import-plan.md)을 따른다. 아래 항목은 계획이며 구현 완료를 의미하지 않는다.

현재 진도: 회사 5개씩 최신 등록 우선 조회, 번호 5개 묶음과 <<, <, >, >> 이동을 구현하고 검증했다. 다음은 가운데 배치·현재 번호 강조와 페이징 경계 상황 정리다. [페이징 진행 기록](company-pagination.md)을 기준으로 한 단계씩 직접 작성한다.

## 다음 버전의 목표

회사 목록을 페이지로 나누고, 서로 다른 사용자가 자체 계정 또는 구글로 로그인해 자기 회사와 지원내역을 관리하도록 확장한다. 다른 사용자의 기록 접근을 차단하고 검증한 웹 서비스를 배포한다. 서버 재시작·업데이트 후 데이터가 유지되며, 중요한 규칙을 자동 테스트로 반복 확인한다. 구현 근거와 시연을 포트폴리오에 연결한다.

기본 CRUD는 2026-10-15에 합의한 범위를 완료했다. 이번 단계는 그 기능을 여러 사용자가 사용할 수 있게 확장하는 작업이다. 카카오·네이버 추가와 확장 프로그램은 이번 배포의 필수 조건이 아니다.

## 현재 확인한 출발점

| 항목 | 2026-10-19 소스·문서 확인 결과 |
| --- | --- |
| 회원·로그인 | Member와 Spring Security 설정·의존성 없음 |
| 데이터 접근 | 회사는 전체 목록, 지원내역은 회사 ID 조건으로 조회. 로그인 회원 범위 제한 없음 |
| 중복 | 서비스의 existsByName / existsByNameAndIdNot 검사. DB 고유 제약 없음 |
| 화면 | HomeController가 전체 회사와 회사별 지원내역을 준비하고 Mustache로 출력 |
| 자동 테스트 | GlobalExceptionHandlerTest 존재. DB 대역을 쓰며 Security 필터 체인과 실제 PostgreSQL 동시 저장 검증은 아님 |
| 데이터 보존 | 개발 설정은 ddl-auto=create, sql.init.mode=always. 실제 이용자 데이터 보관에 그대로 사용하면 안 됨 |
| 포트폴리오 | 로컬 원본에 프로젝트·사례·기여 범위가 있음. 테스트 설명·연락 수단·JobTracker 운영 URL 또는 시연 보완 후보 |

이번 검토에서는 서버·DB를 실행하거나 테스트를 재실행하지 않았다. 기존 실행 결과와 이번 소스 확인을 구분한다.

## 진행 순서와 완료 기준

| 순서 | 할 일 | 완료 기준 |
| --- | --- | --- |
| 0. 기준 정리 | 기존 구현, 미구현, 테스트 범위, 개인 기여를 구분 | 이 계획과 관련 문서가 같은 다음 단계를 안내함 |
| 1. 회사 목록 페이징 | 한 페이지 5개, 번호 5개 묶음, 처음·이전 묶음·다음 묶음·마지막 이동, ID 내림차순 | 0·10·11개 경계, 수정 후 페이지 유지, 등록 후 마지막 페이지, 마지막 항목 삭제 후 페이지 보정 확인 |
| 2. 회원 기본 틀과 자체 로그인 | 회원 필드 재설계, 회원가입, 비밀번호 단방향 해시, Spring Security 세션, 로그인·로그아웃 | 가입·중복·로그인 실패·로그아웃 확인. 평문 비밀번호 저장 금지 |

| 4. 공개 전 검증 | Security가 실제 적용된 요청 테스트, PostgreSQL 제약·동시 저장 테스트, 브라우저 확인 | 미로그인·다른 회원·본인 요청을 구분하고 기존 기능 유지. 결과와 범위를 기록 |
| 5. 데이터 보존과 배포 | 개발/운영 설정 분리, DB 변경 이력, HTTPS·외부 주소·소셜 콜백, 로그 확인·백업 복구 | 외부 브라우저에서 두 계정 사용, 재시작·업데이트 후 기록 유지, 별도 DB 복구 확인 |
| 6. 포트폴리오 보완 | 공개 URL 또는 시연, 실제 사례 설명, 설명 가능한 테스트 근거, 확인된 연락처·기여 범위 | 링크 접근 확인, 개인 정보 없는 시연, 완료한 내용만 소개 |

테스트는 4단계에서 한꺼번에 시작하지 않는다. 1~3단계에서 변경한 규칙을 작게 검증하고 4단계에서 통합 확인한다. 연락처나 기존 사례 설명도 기능 개발이 끝날 때까지 미룰 필요는 없지만, 공개할 정보는 확인받아 사용한다.

## 단계별 설계 기준

### 회원과 접근 권한

- 이전의 구글 전용 Member 네 필드안은 확정 구현안이 아니다. 자체 로그인 시작 시 내부 회원과 로그인 수단을 구분해 필드를 다시 설계한다. 비밀번호는 검증용 단방향 해시만 저장하고, 구글 식별자 (provider, providerId)는 중복을 막는다.
- Company는 회원별 개인 기록이다. 회사의 member 연결로 지원내역의 소유자까지 판단한다. 회원 ID는 클라이언트 입력이 아니라 서버가 확인한 로그인 정보에서 얻는다.
- 홈 화면, 회사 목록·수정·삭제, 회사별 지원 목록·등록, 지원 수정·삭제·상태 변경을 모두 회원 범위로 제한한다. 화면에서 숨기는 것만으로 끝내지 않는다.
- 타인 소유 대상과 없는 대상은 404로 통일하는 안을 기본으로 삼고 구현 전에 API 문서·테스트에 명시한다. 본인 회사에 내역이 없는 경우만 200과 빈 목록을 반환하도록 기존 동작을 조정한다.
- 세션 기반 요청에는 CSRF 보호를 연결한다. 미로그인 API가 로그인 HTML을 성공 응답처럼 처리하지 않도록 오류 응답과 화면 처리를 함께 확인한다.
- 기존 테스트 데이터에 회원을 연결하는 방법은 변경 전에 정한다. 실데이터를 임의로 삭제하거나 첫 로그인 회원에게 몰아주지 않는다.

### 중복과 저장 실패

- 회사 중복의 기본 키는 (member_id, name)이다. 회사명 단독 UNIQUE는 사용하지 않는다. 현재의 정확한 이름 비교를 유지하고, 공백 정리·별칭 통합은 별도 정책으로 다룬다.
- 서비스의 사전 검사는 이해하기 쉬운 안내를 담당하고, DB 제약은 동시에 검사 후 저장되는 요청에도 중복이 남지 않게 한다.
- 고유 제약 위반을 해당 중복 오류로 변환하는 위치와 트랜잭션 경계를 확인한다. 모든 DB 오류를 무조건 회사 중복 409로 바꾸지 않는다.
- 같은 회원·같은 이름의 동시 등록은 한 건만 남고 나머지는 정해진 오류로 끝나야 한다. 다른 회원의 같은 이름은 허용한다. 중복된 이름으로 수정 실패 시 기존 값이 유지되어야 한다.
- 회사 연쇄 삭제의 기존 범위는 유지한다. 회원 삭제·탈퇴 정책까지 cascade로 추측해서 확장하지 않는다.

### 테스트를 배우는 순서

- 먼저 익숙한 '빈 회사명을 보내면 400' 한 사례로 준비 → 요청 → 기대 결과 확인을 이해한다. 이미 존재하는 테스트 전체를 외우거나 전부 새로 만들 필요는 없다.
- 사용자가 작은 입력 조건 또는 기대 결과를 직접 바꾸고 실패·성공 이유를 설명하는 과정을 기록한다. 코드 존재·테스트 통과·작성 경험·이해 여부는 서로 다른 근거다.
- 다음은 본인/타인 기록 접근과 회원별 회사 중복이다. 실제 서비스의 소유자 검사를 검증해야 하며 서비스 전체를 대역 처리한 테스트로 접근 통제를 입증하지 않는다.
- 기존 standalone MockMvc 오류 테스트는 유지할 수 있지만 로그인·CSRF 검증을 대신하지 않는다. Security 필터 체인을 포함하는 테스트와 실제 로그인 브라우저 확인을 추가한다.
- PostgreSQL 제약·동시 저장 검사는 분리된 테스트 DB에서 수행한다. @DataJpaTest라는 이름만 붙였다고 실DB·동시성 검증이 되는 것은 아니다. 실제 연결 대상과 트랜잭션 종료 시점을 확인한다.

### 배포와 이후 DB 변경

- 실제 데이터 입력 전 create·예시 데이터 삽입을 개발 전용으로 분리한다. 운영은 시작할 때 테이블을 재생성하지 않고, 변경 이력을 관리하는 방식으로 스키마를 갱신한다. 기본 후보는 Flyway와 Hibernate validate이며 적용 시 기존 DB 상태를 확인한다.
- 첫 배포는 서버 한 대와 PostgreSQL, 현재 Mustache 구조를 유지한다. 호스팅·AWS 사용 여부는 예산과 운영 부담을 확인해 선택한다. Docker·CI/CD는 필요에 맞춰 한 가지씩 도입하며 배포 전 무조건 모두 요구하지 않는다.
- OAuth 비밀값·DB 비밀번호는 소스에 넣지 않는다. 외부 URL/HTTPS와 콜백 설정을 맞추고 로그인 취소·실패·로그아웃 및 CRUD를 확인한다.
- 백업을 별도 DB에 복원하고, 작은 스키마 변경과 재시작 후에도 기록이 유지되는지 확인한다. 실제 사용자 모집 범위와 데이터 보관·삭제 안내는 공개 전에 정한다.

| --- | --- | --- |
| 회사 검색·상태 필터 | 로그인 회원 식별, DTO·서비스·리포지토리 | 회원 조건과 검색 조건을 함께 적용. 회사 필터인지 지원내역 필터인지 의미 결정 |

| 소셜 계정 연결 | 내부 회원 ID와 그 회원의 기록 | Member 하나에 로그인 계정 여러 개를 연결하는 별도 테이블과 기존 데이터 이전, 양쪽 계정 확인이 필요 |
| 지원내역 가져오기 | 회원별 회사·지원 저장 규칙과 검증 | 출처 기록 ID, 재전송 중복, 한 건 저장 트랜잭션, 확장 프로그램 인증·권한 설계 |
| 화면 개선 | 기존 API와 응답 DTO | 템플릿·CSS 위주 수정. 기존 JS가 찾는 ID·클래스·data 속성도 확인 |

현재 Controller–Service–Repository 구조와 DTO를 유지하므로 프로젝트를 처음부터 다시 만들 필요는 없다. 단, 수정 없이 모든 확장이 되는 것은 아니다. 페이징·계정 연결·확장 프로그램 인증처럼 요구가 달라지는 부분은 그때 설계하고 테스트한다. 미래 기능을 위해 지금 범용 구조나 미사용 필드를 대량으로 만들지 않는다.

## 포트폴리오 피드백 반영 기준

- 채택: 실행 근거, 실제 선택 이유, 확인 가능한 테스트, 개인 기여와 도움 범위, 연락 수단을 명확히 한다.
- 보류: 기능 개수·기술 이름을 늘리기 위한 통계·전면 재디자인·복잡한 회사명 판별. 실제 불편과 사례가 생기면 우선순위를 다시 정한다.
- 테스트 파일이 있다는 사실만으로 본인이 설계·작성했다고 소개하지 않는다. 이해하지 못한 검증 코드를 설명 능력의 근거로 제시하지 않는다.
- 정렬과 삭제 정책 같은 기존 사례는 당시 사실과 지금 추가로 비교한 대안을 구분한다. Debate와 JobTracker의 삭제 목적 차이는 설명 후보이며 사용자 확인 없이 당시 독립 설계 성과로 만들지 않는다.
- 운영 URL은 실제 배포 후, 테스트 결과는 실행 후, 시연은 실제 동작을 기록한 뒤 추가한다. GitHub 공개 접근·연락처·자격증은 확인 없이 추정하지 않는다.
- 현재 공개 포트폴리오를 자동으로 다시 게시하지 않는다. 수정안의 사실 확인과 공개 범위를 확인한 뒤 반영한다.

## 바로 다음 작업과 멈출 기준

회사 페이징의 5개 번호 묶음과 화살표 이동까지 진행했다. 바로 다음 작업은 목록 아래 가운데 배치와 현재 페이지 강조, 이후 빈 목록·범위 밖 요청·삭제 후 페이지 보정이다. 화면 확인을 마친 뒤 자체 로그인용 회원 필드와 가입·로그인 흐름을 정한다. 기존 전체 테스트를 복습하느라 다음 작업을 중단하지 않으며, 개념 학습 여부는 구현·검증 완료 여부와 구분한다.

한 번에 작은 변경을 작성하고 요청 흐름을 설명한 뒤 확인한다. 이해가 막히면 그 변경을 정리한 다음 진행한다. 위 1~6단계가 끝나면 다음 버전 완료로 판단하고 후속 기능은 새 범위로 선택한다. 일정과 채용 성과를 보장하지 않는다.
