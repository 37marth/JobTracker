# JobTracker

회사별 취업 지원내역을 관리하는 Spring Boot 웹 프로젝트입니다. 회사 이름과 위치를 등록하고, 각 회사에 지원한 직무·지원 날짜·메모를 기록합니다. 지원 상태와 관리 화면은 추가할 예정입니다.

## 구현 현황

| 기능 | 상태 |
| --- | --- |
| 회사 등록·목록 조회·이름과 위치 수정 | DTO 적용 후 수동 확인 |
| 회사 응답 DTO | 등록·조회·수정에 적용 |
| 회사명 입력 검증 | 빈 문자열·공백·null 요청의 400 응답 확인 |
| 지원내역 등록·회사별 목록 조회·수정 | 구현 및 수정 후 재조회 확인 |
| 지원내역 응답 DTO | 등록·조회·수정에 적용. 회사 객체 대신 회사 ID를 응답하며 API 확인 완료 |
| 지원내역 입력 검증 | 직무·날짜 필수, 메모 선택. 빈 직무의 400 응답과 메모 null 허용 확인 |
| 수정 대상이 없을 때의 처리 | 404 응답 구현, 실행 확인은 남음 |
| 지원내역 삭제 | 204와 빈 본문, 재삭제 404 확인. 삭제 후 회사와 다른 지원내역 유지 확인 |
| 회사 삭제 | 기본 코드 작성. 지원내역 함께 삭제와 실행 확인은 남음 |
| 지원 상태 | 예정 |
| 회사·지원내역 관리 화면 | 예정. 현재 첫 화면은 제목만 표시 |

## 사용 기술

- Java 17, Spring Boot 4.1.1, Spring Web MVC
- Spring Data JPA, PostgreSQL 18
- Mustache, Validation, Lombok
- Gradle Wrapper 9.7.1

## 사용 흐름

다음 화면 흐름으로 구현할 예정입니다.

1. 회사 이름과 위치를 등록하고 메인 목록에서 확인합니다.
2. 회사를 선택해 지원내역을 확인하고, 직무·지원 날짜·메모를 추가합니다.
3. 결과가 바뀌면 지원 상태와 메모를 수정하고, 잘못 등록한 지원내역은 삭제합니다.
4. 회사를 삭제할 때는 연결된 지원내역도 함께 삭제된다는 경고를 보여주고, 확인한 경우에만 삭제 요청을 보냅니다. 이 연쇄 삭제와 경고창은 아직 미구현입니다.

한 회사에 여러 지원내역을 연결합니다. 다른 직무에 다시 지원할 때는 회사 정보를 재등록하지 않고 지원내역을 추가합니다.

## 실행 방법

JDK 17과 PostgreSQL이 필요합니다.

1. PostgreSQL에 `jobtracker_db`를 생성합니다.
2. `src/main/resources/application.properties`의 접속 주소와 사용자 이름을 환경에 맞춥니다. 기본값은 `localhost:5432/jobtracker_db`, `postgres`입니다.
3. IntelliJ의 프로젝트 SDK와 Gradle JVM을 JDK 17로 설정합니다.
4. `JobtrackerApplication` 실행 설정에 환경변수 `DB_PASSWORD`를 입력합니다.
5. 애플리케이션을 실행하고 `http://localhost:8080/`에 접속합니다.

**현재 `spring.jpa.hibernate.ddl-auto=create`이므로 서버 시작 시 JPA가 관리하는 테이블을 삭제·재생성합니다. 기존 데이터가 지워지므로 별도의 로컬 개발용 DB를 사용합니다.** 테이블 생성 후 `data.sql`이 테스트 회사 두 개를 등록합니다. 재시작 후에도 데이터를 유지하려면 로컬 설정을 `update`로 바꾸고, 테스트 회사가 반복해서 추가되지 않도록 `spring.sql.init.mode=never`로 변경합니다.

서버 실행 후 IntelliJ에서 [jobtracker.http](jobtracker.http)를 열고 원하는 요청 왼쪽의 실행 버튼을 누르면 API를 확인할 수 있습니다. 파일 위쪽의 `companyId`와 `jobApplicationId`를 실제 회사·지원내역 ID에 맞춥니다.

## API

| 메서드 | 경로 | 기능 | 성공 응답 |
| --- | --- | --- | --- |
| GET | `/` | 첫 화면 | 200, HTML |
| POST | `/api/companies` | 회사 등록 | 201, 회사 정보 |
| GET | `/api/companies` | 회사 목록 조회 | 200, 회사 목록 |
| PATCH | `/api/companies/{id}` | 회사 이름·위치 수정 | 200, 회사 정보 |
| DELETE | `/api/companies/{id}` | 회사 삭제 (연쇄 삭제 미구현) | 204, 본문 없음 |
| POST | `/api/companies/{companyId}/job-applications` | 해당 회사의 지원내역 등록 | 201, 지원내역 정보 |
| GET | `/api/companies/{companyId}/job-applications` | 해당 회사의 지원내역 목록 조회 | 200, 지원내역 목록 |
| PATCH | `/api/job-applications/{id}` | 지원 직무·날짜·메모 수정 | 200, 지원내역 정보 |
| DELETE | `/api/job-applications/{id}` | 지원내역 삭제 | 204, 본문 없음 |

목록 조회 결과가 없으면 `[]`을 반환합니다. 수정 요청에는 회사의 이름·위치 또는 지원내역의 직무·날짜·메모를 함께 보냅니다. 위치와 메모는 null을 허용하며, 생략하면 기존 값도 null로 바뀝니다.

회사 등록·조회·수정은 `CompanyResponseDto`로 ID·이름·위치를 응답합니다. 지원내역 등록·조회·수정은 `JobApplicationResponseDto`로 `id`, `companyId`, `jobTitle`, `appliedAt`, `memo`를 응답합니다. 서비스에서 엔티티를 DTO로 변환하고 컨트롤러가 HTTP 상태와 함께 반환합니다. 삭제 응답에는 본문이 없습니다.

수정·삭제 대상이 없으면 404로 응답하도록 구현했습니다. 회사 삭제는 아직 연결된 지원내역을 제거하지 않으므로, 지원내역이 남아 있으면 DB의 참조 관계 때문에 삭제가 거절될 수 있습니다.

### 회사 등록

```http
POST http://localhost:8080/api/companies
Content-Type: application/json

{
  "name": "샘플회사",
  "location": "판교"
}
```

### 지원내역 등록

먼저 등록한 회사의 ID를 주소에 넣습니다. 아래의 `3`은 예시입니다.

```http
POST http://localhost:8080/api/companies/3/job-applications
Content-Type: application/json

{
  "jobTitle": "백엔드 개발자",
  "appliedAt": "2026-09-24",
  "memo": "채용 홈페이지에서 지원"
}
```

## 검증 현황과 남은 작업

회사·지원내역 등록과 목록 조회, 수정 후 재조회를 확인했습니다. 회사명 검증, 빈 지원 직무의 400 응답, 메모 null 허용을 확인했고, 빈 회사명으로 수정한 요청이 거절된 뒤 기존 데이터가 유지되는 것도 확인했습니다. Java 17 컴파일 검사를 통과했으며, 자동 테스트는 아직 실행하지 않았습니다.

응답 DTO 적용 후 회사 API를 수동 확인했고, 지원내역 등록 201·조회 200·수정 200과 수정 후 재조회를 확인했습니다. 지원내역 삭제는 204와 빈 본문, 같은 ID의 재삭제는 404를 확인했습니다. 삭제 후 회사와 기존의 다른 지원내역이 유지되는 것도 확인했습니다. 테스트용으로 등록한 지원내역은 삭제했습니다.

- 회사 삭제 시 연결된 지원내역도 함께 삭제하도록 cascade 구현 및 검증
- 삭제 후 다른 회사와 그 지원내역은 유지되는지 확인
- 수정 대상이 없을 때와 없는 회사 삭제의 404 응답, 날짜만 null인 요청의 400 응답 확인
- 존재하지 않는 회사에 지원내역을 등록할 때의 오류 응답 처리
- 지원 상태 추가, 회사 목록·상세 화면 및 지원내역 관리 화면 연결
- 화면에서 회사 삭제 경고와 취소·삭제 선택 구현

회사 중복 판단 기준은 미정입니다. 검색·필터·페이징, 로그인·통계·배포는 기본 기능 완성 후 검토합니다.

데이터 관계와 처리 흐름은 [아키텍처](ARCHITECTURE.md)에 정리했습니다.
