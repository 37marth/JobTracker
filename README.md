# JobTracker

회사별 취업 지원내역을 관리하는 Spring Boot 웹 프로젝트입니다. 회사 이름과 위치를 등록하고, 각 회사에 지원한 직무·지원 날짜·메모·지원 상태를 기록합니다. 첫 화면에서 회사를 등록하고, 회사 이름을 눌러 해당 회사의 지원내역 전체를 펼쳐볼 수 있습니다.

## 구현 현황

| 기능 | 상태 |
| --- | --- |
| 회사 등록·목록 조회·이름과 위치 수정 | DTO 적용 후 수동 확인 |
| 회사 응답 DTO | 등록·조회·수정에 적용 |
| 회사명 입력 검증 | 빈 문자열·공백·null 요청의 400 응답 확인 |
| 지원내역 등록·회사별 목록 조회·수정 | 구현 및 수정 후 재조회 확인 |
| 지원내역 응답 DTO | 등록·조회·수정에 적용. 회사 객체 대신 회사 ID를 응답하며 API 확인 완료 |
| 지원내역 입력 검증 | 직무의 빈 문자열·공백·null 및 날짜 null의 400 확인. 메모 null 허용 |
| 수정 대상이 없을 때의 처리 | 회사·지원내역 모두 404 응답 확인 |
| 없는 회사에 지원내역 등록 | 404 응답과 등록 거절 후 빈 지원내역 목록 확인 |
| 지원내역 삭제 | 204와 빈 본문, 재삭제 404 확인. 삭제 후 회사와 다른 지원내역 유지 확인 |
| 회사 삭제 | 연결된 지원내역 함께 삭제, 다른 회사와 지원내역 유지 확인. 재삭제 404 확인 |
| 지원 상태 | 첫 등록은 지원완료. 드롭다운 선택 즉시 상태 변경 API 호출, 새로고침 후 선택값 유지 |
| 회사 목록·지원내역 화면 | 회사별 지원내역을 Mustache로 출력. 회사 이름을 누르면 펼치기·접기 |
| 회사 등록 화면 | 입력칸과 등록 버튼을 기존 API에 연결. 성공 시 새로고침 |
| 지원내역 등록 화면 | 회사별 입력칸을 등록 API에 연결. 등록 후 해당 회사가 펼쳐진 상태로 새 내역 표시 |
| 지원 날짜 입력 | 서버의 오늘 날짜를 기본값으로 표시. 사용자가 날짜를 변경할 수 있음 |
| 나머지 관리 화면 | 지원내역 수정·삭제, 회사 수정·삭제와 삭제 확인창은 예정 |

## 사용 기술

- Java 17, Spring Boot 4.1.1, Spring Web MVC
- Spring Data JPA, PostgreSQL 18
- Mustache, Validation, Lombok
- Gradle Wrapper 9.7.1

## 사용 흐름

현재 화면과 후속 작업의 흐름은 다음과 같습니다.

1. 회사 이름과 위치를 등록하고 메인 목록에서 확인합니다.
2. 회사 이름을 누르면 같은 화면에서 직무·지원 날짜·메모·상태를 모두 펼쳐봅니다. 해당 회사 아래의 입력칸으로 지원내역을 추가할 수 있으며, 날짜는 오늘이 기본값이고 직접 변경할 수 있습니다.
3. 결과가 바뀌면 드롭다운에서 지원 상태를 선택해 바로 변경합니다. 메모 수정과 잘못 등록한 지원내역 삭제 API는 구현했으며 화면 연결은 후속 작업입니다.
4. 회사를 삭제할 때는 연결된 지원내역도 함께 삭제됩니다. 화면에서 경고를 보여주고 확인한 경우에만 삭제 요청을 보내는 기능은 추가할 예정입니다.

한 회사에 여러 지원내역을 연결합니다. 다른 직무에 다시 지원할 때는 회사 정보를 재등록하지 않고 지원내역을 추가합니다.

첫 화면을 요청하면 서버가 회사 목록과 각 회사의 지원내역을 조회해 `CompanyViewDto`에 담습니다. Mustache가 지원내역까지 HTML로 만들고, HTML의 `<details>`·`<summary>`가 펼치기와 접기를 처리합니다. 회사 이름을 누를 때 별도의 조회 요청은 보내지 않으며, 최신 데이터는 페이지를 새로고침하면 반영됩니다. 등록 등 데이터를 변경하는 동작에는 기존 API와 `fetch()`를 사용합니다.

지원내역 등록이나 상태 변경이 성공하면 주소 끝에 `#company-회사ID`를 기록하고 페이지를 새로고침합니다. 새로 불러온 페이지에서 해당 회사를 자동으로 펼쳐 최신 지원내역을 바로 볼 수 있게 했습니다. 날짜 기본값은 `HomeController`가 전달하는 서버의 오늘 날짜이며, 등록 요청에는 날짜 입력칸에서 선택한 값을 보냅니다.

## 실행 방법

JDK 17과 PostgreSQL이 필요합니다.

1. PostgreSQL에 `jobtracker_db`를 생성합니다.
2. `src/main/resources/application.properties`의 접속 주소와 사용자 이름을 환경에 맞춥니다. 기본값은 `localhost:5432/jobtracker_db`, `postgres`입니다.
3. IntelliJ의 프로젝트 SDK와 Gradle JVM을 JDK 17로 설정합니다.
4. `JobtrackerApplication` 실행 설정에 환경변수 `DB_PASSWORD`를 입력합니다.
5. 애플리케이션을 실행하고 `http://localhost:8080/`에 접속합니다.

**현재 `spring.jpa.hibernate.ddl-auto=create`이므로 서버 시작 시 JPA가 관리하는 테이블을 삭제·재생성합니다. 기존 데이터가 지워지므로 별도의 로컬 개발용 DB를 사용합니다.** 테이블 생성 후 `data.sql`이 테스트 회사 두 개를 등록합니다. 재시작 후에도 데이터를 유지하려면 로컬 설정을 `update`로 바꾸고, 테스트 회사가 반복해서 추가되지 않도록 `spring.sql.init.mode=never`로 변경합니다.

### API 테스트

[jobtracker.http](jobtracker.http)는 테스트 파일을 찾는 안내입니다. 아래에서 원하는 그룹의 파일을 열고 **1번부터 위에서 아래로** 요청 왼쪽의 실행 버튼을 누릅니다. 각 파일이 테스트 데이터를 준비하므로 다른 그룹을 먼저 실행할 필요는 없습니다.

| 테스트 그룹 | 파일 | 실행 흐름 |
| --- | --- | --- |
| 회사 CRUD | [01-company-crud.http](http/01-company-crud.http) | 목록 → 등록 → 조회 → 수정 → 조회 → 삭제 → 조회 |
| 지원내역 CRUD | [02-application-crud.http](http/02-application-crud.http) | 회사 준비 → 등록·조회·수정·조회·삭제·조회 → 회사 유지 확인 → 회사 삭제·조회 |
| 입력값 검증 | [03-validation.http](http/03-validation.http) | 정상 데이터 준비 → 잘못된 입력 → 기존 값 유지 확인 → 정리 후 회사·지원내역 조회 |
| 회사 연쇄 삭제 | [04-cascade-delete.http](http/04-cascade-delete.http) | 회사 A·B와 지원내역 준비 → A 삭제 → 삭제 범위 확인 → B 정리 후 지원내역·회사 조회 |
| 없는 대상 처리 | [05-not-found.http](http/05-not-found.http) | 등록·조회 → 삭제·조회 → 없는 대상 수정·삭제 및 없는 회사에 등록 시 404 확인 → 지원내역·회사 최종 조회 |
| 지원 상태 변경 | [06-status.http](http/06-status.http) | 준비 → 상태 변경·조회 → 다른 정보 수정 후 상태 유지 → 잘못된 상태 거절·조회 → 삭제·조회 → 없는 대상 404 → 회사 정리·조회 |

등록 응답의 ID는 IntelliJ HTTP Client의 응답 처리 코드가 자동 저장하여 다음 요청에 전달합니다. 숫자를 직접 바꿀 필요가 없으며, 각 그룹은 자신이 만든 데이터만 수정·삭제합니다. 요청 제목의 예상 상태 코드와 주석의 확인 사항을 응답과 비교합니다. 예상과 다르면 멈추고 확인합니다.

중간에 서버를 재시작하면 데이터가 초기화되므로 해당 파일의 1번부터 다시 진행합니다. 정리용 DELETE 다음의 GET까지 실행하여 회사 목록에 테스트 회사가 없는지, 해당 회사의 지원내역 목록이 비었는지 확인합니다. 도중에 멈춘 경우 남은 테스트 데이터를 확인합니다. 05번 파일은 마지막에 삭제한 회사에 지원내역을 등록해 404를 확인하고, 지원내역과 회사 목록을 다시 조회합니다.

## API

| 메서드 | 경로 | 기능 | 성공 응답 |
| --- | --- | --- | --- |
| GET | `/` | 회사 목록과 회사별 지원내역 화면 | 200, HTML |
| POST | `/api/companies` | 회사 등록 | 201, 회사 정보 |
| GET | `/api/companies` | 회사 목록 조회 | 200, 회사 목록 |
| PATCH | `/api/companies/{id}` | 회사 이름·위치 수정 | 200, 회사 정보 |
| DELETE | `/api/companies/{id}` | 회사와 연결된 지원내역 함께 삭제 | 204, 본문 없음 |
| POST | `/api/companies/{companyId}/job-applications` | 해당 회사의 지원내역 등록 | 201, 지원내역 정보 |
| GET | `/api/companies/{companyId}/job-applications` | 해당 회사의 지원내역 목록 조회 | 200, 지원내역 목록 |
| PATCH | `/api/job-applications/{id}` | 지원 직무·날짜·메모 수정 | 200, 지원내역 정보 |
| PATCH | `/api/job-applications/{id}/status` | 지원 상태만 변경 | 200, 지원내역 정보 |
| DELETE | `/api/job-applications/{id}` | 지원내역 삭제 | 204, 본문 없음 |

목록 조회 결과가 없으면 `[]`을 반환합니다. 수정 요청에는 회사의 이름·위치 또는 지원내역의 직무·날짜·메모를 함께 보냅니다. 위치와 메모는 null을 허용하며, 생략하면 기존 값도 null로 바뀝니다.

회사 등록·조회·수정은 `CompanyResponseDto`로 ID·이름·위치를 응답합니다. 지원내역 등록·조회·수정은 `JobApplicationResponseDto`로 `id`, `companyId`, `jobTitle`, `appliedAt`, `memo`, `status`를 응답합니다. 서비스에서 엔티티를 DTO로 변환하고 컨트롤러가 HTTP 상태와 함께 반환합니다. 삭제 응답에는 본문이 없습니다.

지원 상태 변경 요청은 `{"status":"INTERVIEW"}`처럼 상태만 보냅니다. 가능한 값은 `APPLIED`(지원완료), `DOCUMENT_PASS`(서류합격), `INTERVIEW`(면접), `ACCEPTED`(최종합격), `REJECTED`(불합격), `WITHDRAWN`(지원취소)입니다. 상태 누락·null·정의되지 않은 문자열은 400으로 거절하고, 대상이 없으면 404를 반환합니다. 상태 변경 시 직무·날짜·메모는 유지하며, 기존 정보 수정 API도 상태를 유지합니다.

수정·삭제 대상이 없으면 404로 응답합니다. 회사 삭제는 연결된 지원내역도 함께 삭제하며, 다른 회사와 그 지원내역은 유지합니다. 존재하지 않는 회사에 지원내역을 등록하면 404로 거절합니다. 현재 회사별 지원내역 목록 조회는 회사 존재 여부를 검사하지 않아, 없는 회사 ID에도 200과 빈 목록을 반환합니다.

### 회사 등록

```http
POST http://localhost:8080/api/companies
Content-Type: application/json

{
  "name": "샘플회사",
  "location": "판교"
}
```

### 지원내역 등록

먼저 등록한 회사의 ID를 주소에 넣습니다. 아래의 `3`은 예시입니다.

```http
POST http://localhost:8080/api/companies/3/job-applications
Content-Type: application/json

{
  "jobTitle": "백엔드 개발자",
  "appliedAt": "2026-09-24",
  "memo": "채용 홈페이지에서 지원"
}
```

## 검증 현황과 남은 작업

회사·지원내역 등록과 목록 조회, 수정 후 재조회를 확인했습니다. 회사명 검증, 지원 직무의 빈 문자열·공백·null에 대한 400 응답, 메모 null 허용을 확인했습니다. 날짜만 null로 보낸 등록·수정 요청도 400으로 거절되며 새 내역이 생기거나 기존 내역이 바뀌지 않는 것을 확인했습니다. 빈 회사명으로 수정한 요청이 거절된 뒤 기존 데이터가 유지되는 것도 확인했습니다. Java 17 컴파일 검사를 통과했으며, JUnit 테스트는 아직 실행하지 않았습니다.

응답 DTO 적용 후 회사 API를 수동 확인했고, 지원내역 등록 201·조회 200·수정 200과 수정 후 재조회를 확인했습니다. 지원내역 삭제는 204와 빈 본문, 같은 ID의 재삭제는 404를 확인했습니다. 삭제 후 회사와 기존의 다른 지원내역이 유지되는 것도 확인했습니다. 테스트용으로 등록한 지원내역은 삭제했습니다.

회사에 지원내역 두 건을 연결한 뒤 회사 삭제의 204와 빈 본문, 연결된 지원내역 삭제, 다른 회사와 지원내역 유지를 확인했습니다. 지원내역만 삭제하면 회사는 유지되며, 지원내역이 없는 회사도 삭제됩니다. 없는 회사·지원내역의 수정과 삭제는 404를 반환합니다.

존재하지 않는 회사에 지원내역을 등록하면 404로 거절하며, 이후 지원내역 목록이 비어 있고 기존 회사·지원내역도 유지되는 것을 확인했습니다.

지원 상태는 `06-status.http`의 18개 요청을 수동 실행해 확인했습니다. 첫 상태, 상태 변경 후 조회, 다른 정보와 상태의 유지, 잘못된 입력의 400, 없는 대상의 404, 삭제 후 조회를 포함합니다. 회사 목록 화면은 200 응답과 회사 두 개의 이름·위치가 포함된 HTML을 확인했습니다. 목록이 없을 때의 안내 문구는 템플릿에 작성했으며, 빈 목록 화면의 실행 확인은 아직입니다.

2026-10-06에 회사별 지원내역 출력을 Mustache로 변경했습니다. Java 17 빌드를 통과했고, DB에 접속하지 않는 별도 검증 서버에서 기존 API 응답 사본과 추가 예시 데이터를 사용해 실제 `HomeController`와 템플릿을 확인했습니다. HTML 응답에 지원내역이 미리 포함되며, 회사별 펼치기·접기, 여러 지원내역 표시, 빈 목록 안내, 메모 없음 표시와 HTML 문자 처리를 확인했습니다. 기존 DB의 회사·지원내역은 검증 전후 동일했습니다.

2026-10-08 중간점검에서 지원내역 등록 화면과 오늘 날짜 기본값을 코드로 확인하고 Java 17 빌드를 통과했습니다. 현재 서버의 첫 화면은 200으로 응답하며, 날짜 입력칸에 `2026-10-08`이 포함된 것을 확인했습니다. 화면에서 지원내역 등록과 등록 후 회사 펼침 유지 동작은 사용자 수동 확인을 마쳤습니다. 날짜를 변경한 등록 요청은 입력칸의 값을 보내도록 구현했으며, 과거 날짜 선택부터 저장 결과까지의 화면 검증은 별도 확인 항목으로 남겨두었습니다. 이번 점검에서는 조회만 수행했으며, 등록·수정·삭제 API 전체를 다시 실행하지는 않았습니다.

상태 선택 화면은 드롭다운의 `change` 이벤트에서 상태 변경 API를 호출하도록 연결했습니다. 현재 저장된 상태는 HTML의 `data-status`로 전달하고 선택칸의 초기값으로 사용합니다. 브라우저에서 선택 후 새로고침해도 유지되는 동작을 사용자 수동 확인했습니다. 별도 테스트 데이터로 `INTERVIEW`와 `ACCEPTED` 변경의 200, API 재조회 값, 새 HTML의 상태 값 일치와 다른 정보 유지를 교차검증했습니다. 이번 교차검증은 API와 HTML 응답 검사이며 브라우저 클릭 자동화는 수행하지 않았습니다. 테스트 데이터 삭제 후 조회와 기존 데이터 유지를 확인했고, JavaScript 문법 검사도 통과했습니다.
